# E2E-проверки

Playwright-проверки сквозного пути и правил доступа. Работают против запущенных
серверов разработки и базы с синтетическим seed — собственные серверы не поднимают
и тестовую базу integration-тестов не трогают.

## Что нужно для запуска

1. Собранные пакеты: `npm run build:packages`. Тесты импортируют `@context/contracts`,
   `@context/domain` и `@context/testing` через `main`/`types`, то есть из `dist`;
   без сборки набор не запустится.
2. Поднятые сервисы: `npm run dev` (web `:3000`, api `:3001`, worker). Запросы идут
   на web, который проксирует `/api/v1` на api: проверяются те же cookie, Origin и
   CSRF, что и в браузере.
3. Для проекта `chromium` — установленный браузер: `npx playwright install chromium`.
   API-сценарии браузер не используют. Если сборка не установлена (или её версия не
   совпадает с `@playwright/test`), UI-тесты пропускаются с объяснением и командой
   установки, а `npm run test:e2e` не падает.
4. Синтетические данные: `npm run db:seed:demo`. Команда печатает пароли учётных
   записей **один раз** и нигде их не сохраняет; повторный запуск выпускает новые.
5. Переменные окружения с этими паролями (в файлы репозитория они не попадают):

   | Переменная                                        | Назначение                                     |
   | ------------------------------------------------- | ---------------------------------------------- |
   | `E2E_ADMIN_PASSWORD` / `E2E_ADMIN_EMAIL`          | заготовка под Q-04b: сценариев администратора пока нет |
   | `E2E_MANAGER_A_PASSWORD` / `E2E_MANAGER_A_EMAIL`  | руководитель организации А                     |
   | `E2E_MANAGER_B_PASSWORD` / `E2E_MANAGER_B_EMAIL`  | руководитель организации Б                     |
   | `E2E_REVIEWER_A_PASSWORD` / `E2E_REVIEWER_A_EMAIL`| рецензент организации А                        |

   Роль `admin` объявлена в `support/env.ts` и здесь, но ни один тест под
   администратором не входит: путь администратора входит в Q-04b. До тех пор
   переменную можно не задавать.

   Адреса по умолчанию берутся из `packages/testing` (синтетические `*.context.invalid`),
   поэтому обычно достаточно паролей. Если пароль роли не задан, тест не падает,
   а пропускается с указанием недостающей переменной.

   Дополнительно:

   | Переменная                 | Назначение                                                                        |
   | -------------------------- | --------------------------------------------------------------------------------- |
   | `E2E_BASE_URL`             | адрес web, по умолчанию `http://localhost:3000`                                    |
   | `E2E_CHROMIUM_PATH`        | путь к установленному chromium, если автоопределение не подходит                   |
   | `E2E_WORKER_TIMEOUT_MS`    | ожидание черновика заключения от worker, по умолчанию 180 000 мс                   |
   | `E2E_CLEANUP_WAIT_MS`      | ожидание черновика при уборке (его нужно закрыть), по умолчанию 45 000 мс           |
   | `E2E_REQUIRE_CREDENTIALS`  | `1` — пропуск без учётных данных запрещён: прогон падает с названием переменной     |

   `E2E_REQUIRE_CREDENTIALS=1` предназначен для CI: без него прогон без паролей
   даёт «skipped, exit 0», что неотличимо от успешной проверки.

## Запуск

```bash
npm run test:e2e          # все проекты
npm run test:e2e:api      # только API-сценарии, без браузера
npm run typecheck:e2e     # проверка типов тестов (входит в npm run verify)
```

Пароли передаются окружением команды, например через файл вне репозитория:

```bash
set -a; . /path/to/local-e2e.env; set +a; npm run test:e2e:api
```

## Артефакты: почему выключены trace, screenshot и video

`trace` записывает тела запросов и cookie. В trace сквозного пути попали бы пароль
синтетической учётной записи (тело `POST /auth/login`) и значения сессионных
cookie, а html-отчёт скопировал бы `trace.zip` к себе. Поэтому:

- в `playwright.config.ts` `trace`, `screenshot` и `video` выключены и в общем
  `use`, и в каждом проекте; `retries` их не включают;
- репортёр только текстовый (`list`): html-отчёт с вложениями не собирается;
- `test-results/` и `playwright-report/` не выгружаются как артефакты CI.

Для отладки trace включается вручную на один прогон (`npx playwright test --trace on`),
а полученный каталог `test-results/` удаляется сразу после разбора и никуда не
копируется. То же относится к будущим UI-тестам: `page.fill` с паролем тоже попадает
в trace.

## Что покрыто (проект `api`)

| Файл                            | Что проверяет                                                                                                                                             |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api/end-to-end.spec.ts`        | сквозной путь: назначение → ссылка → согласие и ответы участника → черновик от worker → публикация рецензентом → чтение заключения и фиксация решения; в опубликованном заключении нет ключей подсчёта, а дословный текст участника допустим только в свидетельствах и утверждениях вида `self_report` |
| `api/tenant-isolation.spec.ts`  | руководитель организации Б по известным id организации А не читает и не меняет сотрудников, назначения и заключения (ровно 404); в собственной организации нарушителя чужой id отвечает тем же статусом, кодом и текстом, что и несуществующий |
| `api/report-access.spec.ts`     | черновик недоступен без `reports.review`; публикация без права — 403; неполный чек-лист не публикует и даёт отказ, называющий неподтверждённый пункт (фактически `400 VALIDATION_FAILED` от схемы запроса — см. ниже); после публикации заключение доступно руководителю |
| `api/data-exposure.spec.ts`     | ключи подсчёта отсутствуют в проекциях сценариев, методик и во всём ответе попытки участника; сырые ответы и их текст не выдаются руководителю ни одним маршрутом до публикации |
| `api/participant-boundaries.spec.ts` | сессия участника не открывает чужую попытку и кабинет руководителя; перевыпуск ссылки отзывает прежнюю; после отправки ответ не меняется                |
| `api/csrf.spec.ts`              | изменяющий запрос без токена, с чужим токеном и с чужого `Origin` отклоняется и ничего не меняет; сверяется точный текст отказа (источник и защита формы различаются между собой и с обычным отказом по правам); контрольный повтор с правильным `Origin` проходит |

Про строку `report-access`: серверное правило публикации
(`reports.service.ts`, `BUSINESS_RULE_VIOLATION`, 422) сейчас **недостижимо** —
`reviewChecklistSchema` требует по каждому пункту литерал `true`, поэтому
неполный чек-лист отклоняется схемой (`400 VALIDATION_FAILED`) и до сервиса не
доходит. Тест допускает оба кода и сверяет, что отказ называет неподтверждённый
пункт, но проверяет он защиту схемы, а не правило сервиса. Правило сервиса
остаётся непокрытым (см. «Что НЕ покрыто»).

Каждый тест создаёт собственного синтетического сотрудника (`E2E-<метка>`) и
убирает за собой: `cleanup` сначала закрывает подготовленный черновик
заключения (рецензент возвращает его на доработку — `request-revision`, и
черновик уходит из очереди рецензента), затем архивирует сотрудника вместе с
активными назначениями. Записи seed и чужие данные тесты не трогают. Реальных
персональных данных в тестах нет и быть не может. Если уборка не удалась, она не
прячется: причина попадает в аннотацию `cleanup-failed` и в stderr.

Чего уборка сделать не может: **удалить опубликованное заключение**. Продуктового
способа удалить заключение нет, поэтому тесты публикуют только там, где публикация
и есть предмет проверки, а опубликованные синтетические заключения накапливаются в
dev-базе. Это записано как невыполненный критерий Q-04.

### Ручная зачистка остатков

Если прогон прервали, остаются два следа: активные синтетические сотрудники и
черновики заключений в очереди рецензента.

**Черновики.** Рецензент открывает очередь (`/orgs/{org}/reviews`) и по каждому
синтетическому случаю нажимает «Вернуть на доработку» либо запросом:

```bash
# Очередь: caseCode, reportId. Синтетические случаи — те, что тест создал сам.
curl -s -H "cookie: $REVIEWER_COOKIES" "$BASE/api/v1/orgs/$ORG/reviews"

curl -s -X POST -H "cookie: $REVIEWER_COOKIES" -H "x-csrf-token: $CSRF" \
  -H 'content-type: application/json' \
  -d '{"comment":"Уборка после автоматической проверки."}' \
  "$BASE/api/v1/orgs/$ORG/reviews/$REPORT_ID/request-revision"
```

**Сотрудники.** Найти и архивировать их можно из кабинета руководителя (поиск по
`E2E-`, статус «все», действие «Архивировать» с отменой активных назначений) либо
запросом:

```bash
# $BASE — адрес web, $ORG — id организации; cookie сессии и CSRF-токен берутся
# из браузера и в файлы не сохраняются.
curl -s -H "cookie: $COOKIES" \
  "$BASE/api/v1/orgs/$ORG/employees?query=E2E-&status=all&pageSize=100"

# для каждого сотрудника с archivedAt = null:
curl -s -X POST -H "cookie: $COOKIES" -H "x-csrf-token: $CSRF" \
  -H 'content-type: application/json' \
  -d '{"cancelActiveAssignments":true}' \
  "$BASE/api/v1/orgs/$ORG/employees/$ID/archive"
```

## Что НЕ покрыто (Q-04 не закрыта)

Критерии приёмки Q-04 выполнены частично: сделан только контур `api`.

- UI-сценарии трёх ролей (кабинет руководителя, участие, рецензия) — в проекте
  `chromium` пока только smoke-проверка страницы входа.
- Путь администратора из строки E2E ТЗ 12.2: создание организации, редакторы
  методик и сценариев, операции.
- Строка E2E resilience: истёкшая и отозванная ссылка в интерфейсе, вторая
  вкладка, повторные клики, обрыв сети, частичный результат пакетного назначения.
- Доступность: axe на представительных маршрутах, клавиатура и фокус, 200 % zoom,
  reduced motion, мобильные размеры.
- Исследовательский контур: протоколы, снимки, заморозка прогнозов, исходы,
  инварианты слепоты.
- Печатная форма и PDF.
- **Ограничение частоты попыток входа и обмена приглашения.** ТЗ 10.2 требует
  лимит входа по сочетанию «учётная запись + адрес клиента» с защитой от массовой
  блокировки жертвы, ТЗ 10.3 — короткие лимиты на `POST /participant/exchange`.
  В продукте таких лимитов сейчас нет: `@fastify/rate-limit` зарегистрирован с
  `global: false` и ни одним маршрутом не подключён, локаута в `auth.service.ts`
  тоже нет. Проверено эмпирически: 25 неудачных `POST /auth/login` подряд дают
  25 ответов `401 UNAUTHENTICATED`. Поэтому перебор пароля и перебор токена
  приглашения набором не покрыты: пробу на `429 RATE_LIMITED` имеет смысл писать
  вместе с реализацией (отдельная задача и ADR). До тех пор считать периметр
  закрытым по этому пункту нельзя.
- Серверное правило публикации при неполном чек-листе
  (`BUSINESS_RULE_VIOLATION`, 422): недостижимо из-за схемы запроса, поэтому не
  покрыто (см. примечание к таблице выше).
- Удаление собственных заключений: у набора нет продуктового способа убрать
  опубликованные синтетические заключения из dev-базы.
- Прогон в CI: нужен seed и передача паролей в job (там же `E2E_REQUIRE_CREDENTIALS=1`).
  Проверка типов набора (`npm run typecheck:e2e`) в CI уже выполняется отдельным
  шагом job `quality`.

## Известные дефекты, влияющие на E2E

1. **Сценарий с кодом вне `SCENARIO_CODES` не проходит подготовку заключения.**
   Редактор сценариев принимает любой `code` по регулярному выражению
   (`createScenarioInputSchema` в `packages/contracts/src/admin.ts`), а
   `reportContentSchema.scenarioCode` ограничен тремя кодами из `@context/domain`.
   Назначение по такому сценарию доходит до `completed`, затем задание
   `report.generation_requested` падает с `schema_invalid` (`retryable: false`), а
   руководитель видит только состояние «generation_failed» без объяснения. В
   dev-базе так ведёт себя сценарий `probation_review`. Поэтому `createAssignment`
   выбирает сценарий только из `SCENARIO_CODES`. Продуктовое исправление —
   отдельная задача и ADR (запрет публикации сценария с кодом вне перечня либо
   расширяемый перечень), тесты его не маскируют.
2. **Наблюдался редкий `500 INTERNAL_ERROR`** на `GET /orgs/{orgId}/assignments/{id}`
   во время подготовки заключения worker (дважды при первых прогонах). Плотный
   опрос того же маршрута (195 запросов за 45 с во время обработки) повтора не дал.
   Ожидание черновика такие ответы не маскирует: временными считаются только
   502/503/504 и ответы не в JSON (прокси web при перезапуске API), а любой другой
   5xx валит тест с указанием статуса и `requestId`.
3. **Подготовка заключения на общем dev-стенде занимает от 25 до 150 секунд.**
   Диспетчер outbox опрашивает таблицу с интервалом, а стенд делят параллельные
   прогоны и другие агенты, поэтому разброс велик. Из-за этого лимит ожидания
   черновика поднят до 180 с, а лимит теста — до 360 с. Если ожидание снова
   упирается в лимит, смотреть журнал заданий (`/admin/jobs`), а не тест.
4. **События `assignment.completed` навсегда остаются в состоянии `running`**
   в журнале операций: маршрут для них в `apps/worker/src/dispatcher.ts` —
   `null` (очереди нет), событие помечается published, но задание не создаётся
   и «завершённым» не становится. На сквозной путь не влияет, но администратор
   видит десятки вечно «выполняющихся» заданий. Дефект журнала операций,
   отдельная задача.
