# Контекст — платформа оценки сотрудников

Рабочее название: **Контекст**. Название предложено для согласованности примеров; бренд не утверждён.

Дата: **16 сентября 2026**. Версия: **1.1**. Язык продукта и документации: русский.

Сквозной путь работает на синтетических данных: руководитель задаёт вопрос по сотруднику,
сотрудник отвечает по персональной ссылке, система считает результаты и готовит заключение,
человек проверяет его и публикует, руководитель читает основания и фиксирует своё решение.

**Часть разделов не реализована.** Что именно и что не проверялось — в
[передаче работы](docs/knowledge/HANDOFF.md). Статусы задач с доказательствами — в
[roadmap](docs/ROADMAP.md).

**Новое ТЗ для следующего этапа (22.09.2026):** [задание разработчику](TASKS_ROLE2_FRONTEND.md) и [задание специалисту по безопасности](TASKS_ROLE1_ARCH_SECURITY_DEVOPS.md). Эти документы описывают планируемые изменения; текущая реализация ещё следует прежней модели доступа.

## Запуск

### Что нужно на машине

- **Node.js 24.21.0** — закреплён в `.nvmrc`/`.node-version`; `engines` в `package.json` только предупреждает, а не блокирует установку. На Node 20 нативный модуль `argon2` падает с `SIGSEGV` без внятного сообщения — обязательно `nvm use` (или `fnm use`) перед первым запуском.
- **npm 11.19.0** — закреплён в `packageManager`.
- **Docker + Docker Compose** — поднимает только PostgreSQL для локальной разработки (`infra/compose.yaml`). Сам код запускается локально через `npm run dev`, не в контейнере.
- **Python 3** — только для обслуживания пакета документации (`scripts/build_spec.py`, `scripts/check_spec.py`); для запуска продукта не нужен.

### Шаги

```sh
nvm use                             # обязательно — см. про argon2 выше
npm ci
cp .env.example .env
```

Заполнить в `.env`:
- `DB_PASSWORD_API`, `DB_PASSWORD_WORKER`, `DB_PASSWORD_EVALUATOR` — любые локальные пароли; миграция сама создаст под них runtime-роли в PostgreSQL.
- `TOKEN_HASH_SECRET`, `EVALUATOR_SIGNING_KEY` — 32+ случайных байта в base64, например `openssl rand -base64 32`.
- Остальное можно оставить как в `.env.example` (`APP_ENV=development`, `REPORT_PROVIDER=fake`, порты).
- **Не задавайте `NODE_ENV`.** Режим приложения определяет только `APP_ENV`; `NODE_ENV=development` в окружении ломает production-сборку Next.js.

```sh
docker compose -f infra/compose.yaml up -d   # только PostgreSQL: dev на 55442, test на 55443
npm run db:migrate
npm run db:seed:demo                          # печатает синтетические учётные записи и пароли — см. ниже
npm run db:seed:test-data                     # добавляет 6 черновиков назначений, пароли не меняет
npm run dev                                   # web :3000, api :3001, worker в одном терминале
```

Порты PostgreSQL нестандартные (55442/55443) специально, чтобы не конфликтовать с другими проектами на машине.

### Учётные записи для входа

`npm run db:seed:demo` **генерирует новый пароль при каждом запуске и не сохраняет его никуда** — ни в БД в открытом виде, ни в файл репозитория. Единственное место, где пароль виден — вывод команды в терминале в момент запуска; скопируйте его сразу. Это осознанное решение платформы (см. `docs/knowledge/DECISIONS.md`), а не недосмотр — не пытайтесь захардкодить сюда конкретный пароль.

Email всегда одни и те же (заданы в `packages/testing/src/synthetic-people.ts`):

| Email | Роль | Организация | Доступные разделы |
|---|---|---|---|
| `admin@synthetic.context.invalid` | администратор платформы | — | `/admin/*` |
| `manager.a@synthetic.context.invalid` | руководитель, полные права | ООО «Альфа Синтетика» | `/app/*` |
| `reviewer.a@synthetic.context.invalid` | рецензент (только `reports.read`, `reports.review`) | ООО «Альфа Синтетика» | `/app/reviews` |
| `manager.b@synthetic.context.invalid` | руководитель — для проверки изоляции между организациями | ООО «Бета Синтетика» | `/app/*` |

Вход — `http://localhost:3000/login`.

**Сотрудник (участник оценки) не заходит по email/паролю.** Доступ — только по персональной ссылке-приглашению: войдите как `manager.a`, создайте назначение (`/app/assessments/new`) на одного из синтетических сотрудников, откройте карточку назначения и выпустите ссылку. Открывайте её в отдельном приватном окне браузера, чтобы не перепутать сессию руководителя и сессию участника — это разные cookie, но разные окна надёжнее для проверки.

Если нужно перезапустить демо-данные — `npm run db:seed:demo` идемпотентен для организаций/методик/сценариев, но **каждый раз выпускает новые пароли всем аккаунтам**. Если над одной dev-базой параллельно работает несколько человек — договоритесь заранее, кто и когда запускает seed: иначе у остальных внезапно перестанет работать вход посреди работы (это реально происходило, см. `docs/knowledge/HANDOFF.md`, раздел «Известные эксплуатационные особенности»).

Для наполнения экранов назначений после базового seed выполните `npm run db:seed:test-data`. Команда создаёт шесть синтетических черновиков с попытками в двух demo-организациях, не выпускает приглашений и не меняет пароли. Повторный запуск не создаёт дубликаты. Она отказывается работать в `production` и `staging`.

### Проверить, что всё работает

```sh
curl -s http://localhost:3001/api/v1/auth/me    # без сессии — 401 problem+json, не 500
```

В браузере: `/login` → войти под `manager.a@synthetic.context.invalid` → должен открыться `/app` с карточками счётчиков (на чистой базе — нулевыми, но без ошибок).

### Типичные проблемы при первом запуске

- **`argon2` падает с `SIGSEGV` / тесты обрываются без сообщения** — не тот Node. Проверьте `node -v` (нужно `24.21.0`), выполните `nvm use`.
- **Вход перестал работать без видимой причины** — кто-то (в том числе вы сами в другом терминале) повторно запустил `db:seed:demo` и выпустил новые пароли. Запустите его ещё раз и возьмите пароль из свежего вывода.
- **После `npm run db:reset` worker не считает ответы** — сброс удаляет схему очереди `pgboss`, которую worker держит открытой. Перезапустите worker.
- **Странное поведение production-сборки / билд ведёт себя не так** — проверьте, что `NODE_ENV` не задан в `.env`; режим приложения — только `APP_ENV`.
- **`docker compose -f infra/compose.app.yaml up`** (api/worker/web целиком в контейнерах) — путь существует, но по состоянию на 17.09.2026 никогда не проверялся целиком end-to-end, только отдельные образы отдельно. Для повседневной разработки используйте `infra/compose.yaml` (только Postgres) + `npm run dev`.

## Обновление документации

Источники истины: модули `docs/spec/`, база знаний и `docs/roadmap.json`. Сводный промпт и markdown-roadmap генерируются из них.

```sh
python3 scripts/build_spec.py
python3 scripts/check_spec.py
```

Python нужен только для обслуживания этого пакета документов. Продукт должен использовать TypeScript / Node.js / npm.

## Главная продуктовая граница

Платформа собирает данные и формирует объяснимое заключение для рассмотрения руководителем. Само наличие нескольких тестов и AI не доказывает прогноз ухода, успех повышения или окупаемость обучения. Неизвестные методики, лицензии и права на данные отражены в [открытых вопросах](docs/knowledge/OPEN_QUESTIONS.md). Они блокируют соответствующее применение к реальным сотрудникам, но не разработку на синтетических примерах.
