# Runbook эксплуатации

Документ описывает эксплуатацию платформы «Контекст»: установку с нуля, запуск и
остановку, миграции и откат, секреты и их ротацию, проверки состояния, резервное
копирование и восстановление, первого администратора, восстановление доступа,
приостановку организации, разбор упавших заданий, отзыв ссылок, удаление данных,
обработку инцидента и наблюдаемость (состав по ТЗ 12.7).

Разделы, где процедура описана, но **не реализована** в продукте, помечены как
невыполненные критерии прямо в тексте: § 8 (первый администратор), § 9 (сброс пароля
администратором), § 10 (остановка участников при приостановке организации),
§ 12 (отзыв ссылки без отмены назначения), § 13 (удаление данных, Q-01), § 15 (метрики).

Каждый раздел помечен:

- **проверено 17.09.2026** — команда выполнялась в этой среде, результат приведён;
- **не проверялось** — порядок описан, но фактического прогона не было. Такие пункты
  нельзя считать готовыми (ТЗ 12.6).

Среда проверки: macOS, Docker 29.1.3, Node 24.21.0, PostgreSQL 18.6 в контейнере,
только синтетические данные.

## 1. Установка с нуля (локально)

**Проверено 17.09.2026** для установки по lockfile внутри образов; локальная установка
на хосте выполнялась ранее (см. `docs/knowledge/HANDOFF.md`).

```sh
node --version                     # должно совпасть с .nvmrc: v24.21.0
npm ci                             # только lockfile; yarn/pnpm не использовать
cp .env.example .env               # заполнить пароли ролей и TOKEN_HASH_SECRET
docker compose -f infra/compose.yaml up -d postgres
npm run db:migrate                 # схемы, роли, RLS, схема очереди
npm run db:seed:demo               # синтетические организации и учётные записи
npm run dev                        # web :3000, api :3001, worker
```

`npm run db:seed:demo` печатает синтетические учётные записи и пароли — это
демонстрационные данные, в репозиторий и в журналы они не попадают.

Генерация секретов:

```sh
openssl rand -base64 32            # TOKEN_HASH_SECRET, EVALUATOR_SIGNING_KEY
openssl rand -base64 24            # пароль runtime-роли
```

**Пароль в строке подключения должен быть percent-encoded.** `base64` регулярно даёт
`+`, `/` и `=`; `/` и `@` ломают разбор URL, а `+` в userinfo — это именно символ `+`,
а не пробел. Кодируйте значение перед подстановкой:

```sh
node -e 'process.stdout.write(encodeURIComponent(process.argv[1]))' "$PASSWORD"
```

Скрипты эксплуатации декодируют только `%XX` (`scripts/ops/lib.sh`), обратные слэши и
`+` остаются собой.

## 2. Запуск из образов

**Проверено 17.09.2026:** сборка образов api, worker, web; запуск контейнера api
против базы разработки и обе проверки состояния. Запуск всего манифеста
`infra/compose.app.yaml` целиком **не проверялся**.

```sh
docker build -f infra/docker/api.Dockerfile    --build-arg NODE_VERSION=$(cat .nvmrc) -t context-api .
docker build -f infra/docker/worker.Dockerfile --build-arg NODE_VERSION=$(cat .nvmrc) -t context-worker .
docker build -f infra/docker/web.Dockerfile    --build-arg NODE_VERSION=$(cat .nvmrc) \
  --build-arg API_INTERNAL_URL=http://api:3001 -t context-web .
```

Свойства образов: non-root (`node`, uid 1000), код принадлежит root и только читается,
секретов и build args с секретами нет, версия Node сверяется с `.nvmrc` при сборке.

Запуск поверх отдельной базы:

```sh
cp infra/app.env.example .env.app          # заполнить подключения и ключи
docker compose -f infra/compose.app.yaml --env-file .env.app run --rm migrate
docker compose -f infra/compose.app.yaml --env-file .env.app up -d
```

Порядок обязателен: `migrate` — отдельная одноразовая команда под ролью владельца
схемы, сервис `api` стартует только после её успешного завершения. Приложение
работает runtime-ролями (`context_api`, `context_worker`) без DDL и без BYPASSRLS.

Особенности:

- `API_HOST` в контейнере равен `0.0.0.0`; по умолчанию (и в dev) API слушает только
  loopback. Наружу api и web выходят через общий reverse proxy с одним origin.
- Адрес API для rewrites у web фиксируется **на этапе сборки** (`API_INTERNAL_URL`):
  Next записывает rewrites в манифест при `next build`.
- У worker нет публичного порта и HTTP-проверки: его состояние видно по коду выхода
  процесса и по экрану обработки администратора.
- `NODE_ENV=development` в окружении ломает production-сборку Next. Режим приложения
  задаётся только `APP_ENV`.

## 3. Миграции

**Проверено 17.09.2026** (сверка контрольных сумм миграций восстановленной базы).

```sh
npm run db:migrate                 # применить новые файлы
npm run db:migrate -- --reset      # пересоздать схемы; запрещено при APP_ENV=production|staging
```

- Каждая миграция применяется в одной транзакции и записывается в
  `public.schema_migrations` вместе с sha256 файла.
- Изменение уже применённого файла — ошибка: нужна новая миграция.
- Миграции применяет только владелец схемы (`DATABASE_URL_MIGRATOR`). Он же задаёт
  пароли runtime-ролей из `DB_PASSWORD_API`/`WORKER`/`EVALUATOR`.
- Откат: отдельной команды нет. Обратная миграция пишется файлом; аварийный откат —
  восстановление из резервной копии (раздел 6). **Не проверялось.**

## 4. Секреты

Хранятся в secret manager окружения, в репозитории — только `.env.example` и
`infra/app.env.example` с placeholder-значениями. В URL, localStorage, тексты ошибок
и метрики секреты не попадают.

| Переменная                                  | Кому нужна | Назначение                                |
| ------------------------------------------- | ---------- | ----------------------------------------- |
| `DATABASE_URL_MIGRATOR`                     | migrate    | владелец схемы, DDL и роли                |
| `DATABASE_URL_API` / `_WORKER`              | api/worker | runtime-роли без DDL и BYPASSRLS          |
| `DB_PASSWORD_API` / `_WORKER` / `_EVALUATOR` | migrate    | пароли runtime-ролей                      |
| `TOKEN_HASH_SECRET`                         | api        | HMAC хэшей токенов приглашений и сессий   |
| `EVALUATOR_SIGNING_KEY`                     | api        | подпись внутреннего контекста исходов     |
| `BACKUP_SOURCE_URL` / `RESTORE_TARGET_URL`  | эксплуатация | роль копий и восстановления (§ 6.0), только на время операции |

### Ротация `TOKEN_HASH_SECRET`

**Не проверялось.** Смена секрета делает недействительными все выданные ссылки
участников и сессии: в базе лежат только HMAC-хэши, пересчитать их без исходных
токенов нельзя.

Порядок:

1. Предупредить организации: выпущенные ссылки перестанут открываться.
2. Сменить значение в secret manager, перезапустить api.
3. Выпустить ссылки заново тем назначениям, которые ещё не завершены (повторный
   выпуск отзывает прежнюю ссылку).
4. Записать событие в журнал эксплуатации.

Плавная ротация с двумя действующими секретами сейчас не поддерживается: в коде один
`TOKEN_HASH_SECRET`. Если такое требование появится — это отдельное решение (ADR).

Пароли runtime-ролей ротируются проще: новое значение в `DB_PASSWORD_*` и повторный
запуск команды миграции (`ALTER ROLE ... PASSWORD`), затем перезапуск api и worker.

## 5. Проверки состояния

**Проверено 17.09.2026** на контейнере api против базы разработки:

```sh
curl -s localhost:3001/health/live    # {"status":"ok"} — БД не опрашивается
curl -s localhost:3001/health/ready   # {"status":"ok","checks":{"database":true,"migrations":true}}
```

- `/health/live` — живость процесса; используется в `HEALTHCHECK` образа api.
- `/health/ready` — доступность базы и наличие применённых миграций. `degraded`
  означает «не отправлять трафик», а не «упал».
- Версии, строки подключения и названия организаций в ответах не выводятся.

## 6. Резервное копирование и восстановление

Скрипты: `scripts/ops/backup.sh`, `scripts/ops/restore.sh`, `scripts/ops/verify-restore.sh`,
`scripts/ops/deletion-fences.sql`, `scripts/ops/fence-drill.sql`.

Версии клиентских утилит должны совпадать с сервером; если на машине другой psql,
укажите контейнер: `PG_CONTAINER=context-postgres`. При заданном `PG_CONTAINER`
утилиты запускаются **внутри** контейнера, поэтому `scripts/ops/lib.sh` заменяет
host/port строки подключения на внутренние (`PG_CONTAINER_HOST`/`PG_CONTAINER_PORT`,
по умолчанию `127.0.0.1:5432`) и сообщает об этом в выводе. Опубликованный порт хоста
(55442/55443) изнутри контейнера недоступен.

### 6.0. Роли для копий и восстановления

**Обязательное требование, а не рекомендация.** На таблицах включён
`FORCE ROW LEVEL SECURITY` (миграция `0008_rls_and_grants.sql`). Под ролью без
`BYPASSRLS`:

- `pg_dump` отказывает: `query would be affected by row-level security policy for
  table "access_grants"` — копию снять нельзя вовсе;
- `deletion-fences.sql` и `verify-restore.sql` увидели бы **ноль строк** и отчитались
  бы об успехе, ничего не оградив и ничего не проверив.

Поэтому все три скрипта начинаются с `set row_security = off` и явной проверки роли:
роль без `BYPASSRLS` получает ошибку на русском, а не тишину.

Роль миграций (`DATABASE_URL_MIGRATOR`) для этого **не подходит**:
`packages/database/src/cli/migrate.ts` запрещает владельцу схемы иметь `BYPASSRLS` в
production-подобных окружениях и падает при старте.

Нужны две отдельные роли, живущие только для этих операций. Пароли берутся из secret
manager, в `.env` разработки и в манифестах compose эти роли не хранятся.

#### Роль копий — минимальная

```sql
create role context_backup login bypassrls password :'password';
grant pg_read_all_data to context_backup;   -- только чтение, без владения и DDL
grant connect on database context to context_backup;
```

`pg_read_all_data` даёт `SELECT` на всё и ничего больше; `BYPASSRLS` нужен отдельно —
этот предопределённый роль-атрибут политики RLS не снимает. Владельцем объектов роль
не является и DDL выполнять не может — это проверяемое утверждение, а не обещание.

#### Роль восстановления — фактически владелец схемы

```sql
create role context_restore login bypassrls createdb createrole password :'password';
grant context_owner to context_restore;
```

- `BYPASSRLS` — иначе ограды и проверки работают вхолостую;
- `CREATEDB` — `restore.sh` создаёт новую базу;
- `CREATEROLE` — `restore.sh` создаёт недостающие runtime-роли и выдаёт себе членство
  в них (это нужно функциональной проверке RLS, см. ниже);
- членство в `context_owner` — без него `pg_restore` не может выполнить
  `alter table … owner to context_owner`.

**Честно о радиусе поражения: это роль с полными правами владельца схемы, включая
DDL, плюс `BYPASSRLS`.** Прежняя редакция этого раздела предлагала
`alter role context_restore noinherit` и утверждала, что «владельцем роль работает
только через `set role`, собственных прав на DDL у неё нет». Это неверно и
**проверено 17.09.2026**: на PostgreSQL 16+ признак наследования фиксируется в момент
`GRANT`, и последующий `ALTER ROLE … NOINHERIT` его не меняет.

```
 rolname         | rolinherit | inherit_option | set_option | admin_option
-----------------+------------+----------------+------------+--------------
 context_restore | f          | t              | t          | f
```

`inherit_option = t` при `rolinherit = f`: роль пользуется правами владельца без
единого `set role`. Вариант `grant … with inherit false` жизнеспособным не является:
он лишает роль прав владельца, но `BYPASSRLS` — атрибут самой роли и никуда не
девается, а `pg_restore` без прав владельца не отработает.

Поэтому ограничение здесь организационное, а не техническое: отдельная учётная
запись, пароль в secret manager, выдаётся на время операции и отзывается после неё,
все действия видны в журнале сервера. `SUPERUSER` роли не выдаётся — это единственная
привилегия, которой у неё действительно нет.

#### Владелец восстановленной базы

`restore.sh` создаёт базу с владельцем `RESTORE_DB_OWNER` (по умолчанию
`context_owner`), а не ролью подключения. Иначе схема `public` достаётся
`pg_database_owner` = эксплуатационной роли, и `pg_restore` падает на
`alter table public.schema_migrations owner to context_owner`:
`permission denied for schema public`. В среде разработки это не всплывает, потому что
там подключаются самим владельцем.

#### Функциональная проверка RLS и членство в runtime-ролях

`verify-restore.sql` проверяет, что `context_api` без контекста организации не видит
ни строки. Для этого нужен `set role context_api`, а он требует членства в целевой
роли. Эксплуатационная роль членом runtime-ролей не является: команда миграции
создаёт их без `grant` владельцу.

- если роли создаёт сам `restore.sh` — он получает на них `ADMIN OPTION` и выдаёт себе
  членство `with inherit false, set true` (права не подмешиваются, роль только может
  ими стать);
- если роли уже существуют и членство выдать нечем, `restore.sh` печатает
  `NOTICE: Нет права выдать членство в роли … — функциональная проверка RLS пойдёт по
  каталогу`, а `verify-restore.sql` выполняет проверку по каталогу политик и прямо
  пишет об этом в подробности. Восстановление из-за этого не прерывается.

Выдать членство вручную может администратор кластера:

```sql
grant context_api, context_worker, context_evaluator to context_restore
  with inherit false, set true;
```

**Проверено 17.09.2026 на кластере, где владелец схемы НЕ суперпользователь** —
отдельный контейнер `postgres:18`, роль `context_owner` создана как
`nosuperuser nocreatedb nocreaterole nobypassrls`. Полный цикл (копия ролью
`context_backup` → `restore.sh` → `verify-restore.sh`) проходит, обе ветви проверки
RLS (через `set role` и по каталогу) отработали, фактический вывод — в § 6.4.

### 6.1. Копия

**Проверено 17.09.2026** на базе разработки под ролью копий `context_backup`
(`BYPASSRLS` + `pg_read_all_data`, без владения объектами — § 6.0). Команда
исполнялась ровно в этом виде:

```sh
BACKUP_SOURCE_URL="postgresql://context_backup:<пароль>@127.0.0.1:55442/context" \
PG_CONTAINER=context-postgres \
  scripts/ops/backup.sh backups
```

Фактический вывод (сокращённо):

```
Подключение внутри контейнера context-postgres: адрес 127.0.0.1:55442 заменён на 127.0.0.1:5432.
Открываю транзакцию-держатель снимка…
Снимок: 00000049-00000464-1
Создаю дамп: backups/context-20260917T064350Z.dump
Снимаю количества строк в снимке дампа…
  дамп:     571 992 байт, sha256 8c0886bf…
  манифест: backups/context-20260917T064350Z.manifest
```

Даёт `<база>-<дата>.dump` (custom format) и `.manifest` с количествами строк, списком
миграций и контрольными суммами, версией сервера, числом политик и таблиц с FORCE RLS,
а также sha256 дампа. Состава runtime-ролей в манифесте нет: роли — глобальные объекты
кластера, их наличие и свойства проверяются по каталогу восстановленного сервера
(§ 6.4). Манифест не содержит персональных данных и секретов; дамп содержит — хранить
только в зашифрованном хранилище и удалять по утверждённому сроку (§ 6.6).

Файлы создаются с `umask 077` (`-rw-------`, каталог `drwx------`): на общей
эксплуатационной машине незашифрованный дамп не должен читаться другими локальными
пользователями. **Проверено 17.09.2026** — права файлов после прогона именно такие.

**Количества строк снимаются в снимке самого дампа.** Скрипт открывает транзакцию
`repeatable read`, экспортирует снимок (`pg_export_snapshot`), передаёт его
`pg_dump --snapshot=<id>` и считает строки в той же транзакции. Поэтому сверка при
восстановлении строгая: «база менялась во время дампа» больше не является причиной
понизить расхождение до предупреждения.

**Проверено 17.09.2026:** во время дампа в копируемую базу параллельно писались
198 синтетических записей `platform.audit_events`. В манифесте — 635 строк, в базе
после дампа — 833; восстановленная копия дала ровно 635, строгая сверка пройдена.

Манифесты, снятые прежней версией скрипта (ключ `counts_stable`), `verify-restore.sh`
отвергает: их количества к снимку дампа не относятся.

### 6.2. Восстановление

**Проверено 17.09.2026** на кластере, где владелец схемы НЕ суперпользователь
(отдельный контейнер `postgres:18`, роль `context_owner` создана как
`nosuperuser nocreatedb nocreaterole nobypassrls`). Команда исполнялась в этом виде
(пароль — из окружения, в команду не подставляется):

```sh
RESTORE_TARGET_URL="postgresql://context_restore:${RESTORE_PW}@127.0.0.1:55444/context_restore_check" \
PG_CONTAINER=context-restore-probe \
  scripts/ops/restore.sh backups/context-20260917T064350Z.dump
```

Шаги скрипта: **сверка sha256 дампа с манифестом** → создание недостающих
runtime-ролей и выдача себе членства в них → создание базы с локалью ICU `ru-RU` и
владельцем `RESTORE_DB_OWNER` → `pg_restore --exit-on-error` → `analyze` таблиц
приложения → **ограды удаления**.

Фактический вывод (сокращённо):

```
0/5 Сверяю контрольную сумму дампа с манифестом context-20260917T064350Z.manifest…
      sha256 совпадает.
1/5 Создаю недостающие runtime-роли (без паролей: их задаёт команда миграции)…
NOTICE:  Создана роль context_api
NOTICE:  Роли context_api выдано членство текущему пользователю (для проверки RLS)
2/5 Создаю базу context_restore_check (владелец context_owner, локаль ICU ru-RU)…
3/5 Восстанавливаю дамп (571992 байт)…
4/5 Обновляю статистику планировщика (analyze)…
5/5 Применяю ограды удаления…
```

Важные детали, выявленные именно на не-суперпользовательском кластере:

- **владелец базы** берётся из `RESTORE_DB_OWNER` (по умолчанию `context_owner`), а не
  из строки подключения. С владельцем-эксплуатационной ролью `pg_restore` падал на
  `alter table public.schema_migrations owner to context_owner` —
  `permission denied for schema public`;
- **`analyze`** выполняется только по таблицам приложения и очереди. `analyze` без
  аргументов под ролью без `SUPERUSER` печатает десяток

Без манифеста восстановление не начинается: целостность копии подтвердить нечем.
Осознанное исключение — `RESTORE_NO_MANIFEST=1` (скрипт скажет об этом в выводе).

### 6.3. Ограды удаления

Восстановленная копия содержит данные на момент снимка: всё, что удалено позже, в ней
«живо». До открытия базы приложению применяются ограды (ТЗ 10.8 п. 6):

1. назначения под оградой получают `processing_hold`;
2. тем из них, по которым в копии остались **живые задания очереди** или
   **неостановленные события outbox** действующего поколения, поднимается
   `data_generation`;
3. ссылки участников и сессии по ним отзываются;
4. неопубликованные события outbox останавливаются;
5. задания очереди со старым поколением обработчик пропускает сам — он сверяет
   `data_generation` в своей транзакции.

**«Живое» задание — это любое незавершённое состояние pg-boss**, то есть всё, кроме
`completed`, `cancelled` и `failed`. Прежняя редакция смотрела только на
`created`/`retry` и пропускала самое вероятное состояние в момент аварии — `active`
(задание взято в работу). pg-boss возвращает просроченное `active` в `retry` по
истечении `expire_seconds` (по умолчанию 900 с) и отдаёт обработчику задание с
совпадающим `dataGeneration`. **Проверено 17.09.2026** на учебной ситуации из трёх
назначений: прежний фильтр поднял бы поколение двум из трёх, текущий — всем трём.

Поколение поднимается **по факту наличия живой работы, а не по признаку hold**.
Назначение, у которого `processing_hold` стоял уже в момент снимка (именно так его
помечает приём запроса на удаление), иначе сохранило бы действующее поколение: его
задание прошло бы сверку и выполнилось по восстановленным данным, как только hold
снимут. Идемпотентность от этого не страдает: после подъёма поколения совпадений нет,
а остановленные события outbox из условия выпадают.

Что попадает под ограду:

- незавершённые запросы по данным `platform.privacy_requests` типов `deletion` и
  `withdrawal` (состояние не `rejected`/`completed`);
- незавершённые задания `platform.deletion_jobs` (`queued`/`running`/`failed`),
  в том числе упавшие;
- назначения с отозванным согласием — `core.consent_records.withdrawn_at is not null`
  (платформа хранит отзыв согласия отдельно от `privacy_requests`);
- идентификаторы из внешнего журнала `RESTORE_FENCE_IDS`.

**Что оградой не покрыто.**

1. **Ограда не удаляет воскресшее содержание.** Для назначений из внешнего журнала
   (`RESTORE_FENCE_IDS`, то есть удалений, исполненных ПОСЛЕ снимка) скрипт ставит
   `processing_hold`, отзывает ссылки и сессии и останавливает outbox, но
   `core.answers`, `core.attempts`, `core.reports` и `core.report_revisions` остаются
   в копии как есть. `processing_hold` читают только обработчики
   (`apps/worker/src/jobs/score-attempt.ts`, `generate-report.ts`) и проверка
   возможности повтора задания (`admin-operations.service.ts`); на путях чтения
   ответов и отчётов руководителем и администратором он не проверяется.
   **Следствие:** восстановленную копию нельзя открывать пользователям продукта до
   повторного исполнения удаления. Пока процесс удаления (Q-01) не реализован,
   ТЗ 10.8 п. 6 закрыт частично — это невыполненный критерий, а не особенность.
2. **`core.participation_declines`** (отказ от участия). Отказ — не запрос на удаление
   данных и поколение данных не меняет; повторную обработку такого назначения
   останавливает резолвер `app.resolve_job_target` (миграция `0012`) в самом задании.
   Если потребуется закрывать отказы оградой, это отдельное решение.

Удаления, исполненные **после** снимка, в копии не видны. Их список передаётся извне
копии — из журнала исполненных запросов по данным:

```sh
RESTORE_FENCE_IDS='{uuid-назначения,uuid-назначения}' scripts/ops/restore.sh <дамп>
```

**Ограничение, не закрытое сейчас:** такого журнала вне базы платформа пока не ведёт —
процесс удаления (Q-01) не реализован. Пока он не появится, полнота оград зависит от
ручного списка. Это невыполненный критерий, а не особенность.

### 6.6. Очистка локальных копий

Дамп на локальном диске лежит **незашифрованным** и содержит полное содержание базы.
Файлы создаются с `umask 077`, но это защита от соседа по машине, а не замена
шифрованию: после проверки дамп нужно удалить или переложить в зашифрованное
хранилище — скрипт говорит об этом в конце вывода.

```sh
# удалить локальные дампы, их манифесты и журналы старше суток (текущий не трогается)
BACKUP_DELETE_AFTER_SECONDS=86400 scripts/ops/backup.sh backups
```

Манифест удаляется **вместе со своим дампом**: иначе в каталоге копятся манифесты без
дампов, и `restore.sh` рядом с новым дампом может подобрать чужой манифест, а оператор
принять осиротевший набор за копию. Манифест, у которого дампа не было изначально,
скрипт не трогает — удаление привязано к дампу. **Проверено 17.09.2026:** из каталога
с парой `*.dump`/`*.manifest`/`*.log` старше срока удалены все три файла.

Для учебных прогонов: каталог копий и временная база восстановления удаляются сразу
после `verify-restore.sh`. **Проверено 17.09.2026:** после прогона в каталогах
репозитория и во временном каталоге сессии файлов `*.dump` и `*.manifest` не осталось,
пробный контейнер `context-restore-probe` и роль копий `context_backup` удалены.

## 7. Остановка и запуск процессов

**Проверено 17.09.2026** только для разработки и отдельных контейнеров; остановка и
запуск всего манифеста `infra/compose.app.yaml` **не проверялись** (dev-порты и база
заняты).

Разработка:

```sh
npm run dev            # api, worker, web одной командой; Ctrl+C останавливает все три
npm run dev:api        # по отдельности, когда нужен перезапуск одного процесса
npm run dev:worker
npm run dev:web
```

Из образов:

```sh
docker compose -f infra/compose.app.yaml --env-file .env.app stop web api worker
docker compose -f infra/compose.app.yaml --env-file .env.app start worker api web
docker compose -f infra/compose.app.yaml --env-file .env.app restart api
```

Порядок имеет значение:

- **остановка** — web → api → worker: сначала перестаём принимать запросы, потом
  останавливаем фоновую обработку. Незавершённые задания очереди остаются в
  `pgboss.job`; pg-boss вернёт просроченное `active` в `retry` после
  `expire_seconds` (по умолчанию 900 с), и задание выполнится после запуска;
- **запуск** — `migrate` (одноразовая команда) → api → worker → web. Сервис `api`
  стартует только после успешной миграции.

У worker нет HTTP-порта и проверки состояния: его живость видна по коду выхода
процесса и по экрану обработки администратора (§ 15). После `npm run db:reset` и
`npm run db:seed:demo` worker нужно перезапускать вручную — роли и схема очереди
пересоздаются, и прежнее подключение становится недействительным.

## 9. Восстановление доступа

**Не проверялось** на стенде: проверка потребовала бы входа синтетическими учётными
записями в базу разработки, которую сейчас используют другие работы.

**Участник потерял ссылку.** Руководитель выпускает ссылку заново:

```
POST /api/assignments/:assignmentId/invitations
```

Повторный выпуск **отзывает прежнюю ссылку и активные сессии по ней** — старая ссылка
перестаёт открываться сразу.

**Руководитель забыл пароль.**

1. Руководитель отправляет заявку: `POST /api/auth/recovery-requests`. Ответ одинаков
   независимо от того, существует такой адрес или нет; писем система не отправляет,
   в базе остаётся только факт обращения (`identity.recovery_requests`) без адреса в
   открытом виде.
2. Заявка видна администратору в обзоре (`GET /api/admin/overview`).
3. После проверки личности вне системы администратор организации выпускает новую
   ссылку активации: `POST /api/organizations/:orgId/members/:membershipId/invitation`.
4. Переход по ссылке (`POST /api/auth/activate`) задаёт новый пароль, гасит остальные
   выпущенные ссылки этого пользователя и открывает сессию.

**Ограничение:** `POST /api/auth/password-reset` принимает токен с назначением
`password_reset`, но такой токен сейчас **ничем не выпускается** — реализован только
путь через ссылку активации. Это невыполненный критерий.

**Чужая сессия.** `GET /api/auth/sessions` показывает активные сессии,
`POST /api/auth/sessions/revoke-others` закрывает все, кроме текущей. Смена пароля
(`POST /api/auth/password/change`) закрывает остальные сессии сама.

## 10. Приостановка организации

**Не проверялось** (см. § 9 — вход в базу разработки сейчас недоступен для проверок).

```
POST /api/admin/organizations/:orgId/suspend   { "reason": "…" }
POST /api/admin/organizations/:orgId/resume
```

Обе операции пишутся в аудит (`organization.suspended` / `organization.resumed`) вместе
с причиной.

Что приостановка делает и чего не делает:

- **делает:** резолвер членств `app.resolve_user_memberships` (миграция `0009`) отдаёт
  только организации со статусом `active`. Руководители этой организации теряют доступ
  при следующем запросе;
- **не делает:** ссылки участников и их сессии продолжают работать — резолверы
  `app.resolve_participant_session` и `app.resolve_invitation` статус организации не
  проверяют. Фоновая обработка (worker) тоже не останавливается.

Поэтому «приостановить организацию полностью» — это последовательность: приостановка,
затем отмена незавершённых назначений (§ 12), которая отзывает ссылки и сессии.
Автоматической остановки участников и обработки по статусу организации в коде нет —
**невыполненный критерий**.

## 11. Упавшее задание

**Не проверялось** на стенде.

Администратор работает с событиями доставки (`platform.outbox_events`), а не напрямую
с очередью pg-boss:

```
GET  /api/admin/jobs?state=failed        # список; фильтры — GET /api/admin/operations/facets
GET  /api/admin/jobs/:jobId              # подробности и перечень блокировок повтора
POST /api/admin/jobs/:jobId/retry        # повторить
POST /api/admin/jobs/:jobId/retries      # { "stopped": true } — прекратить попытки
```

Повтор отклоняется с объяснением, если задание больше не должно исполняться
(`admin-operations.service.ts`, `retryBlockers`):

- поколение данных изменилось после постановки задачи (отзыв, удаление, ограда
  восстановления);
- назначение отменено или его срок истёк;
- обработка приостановлена по запросу о данных (`processing_hold`);
- участник отказался от участия;
- согласие участника не действует.

Разбор: сначала причина в подробностях задания и в аудите (`GET /api/admin/audit`),
затем журнал worker. Заданиями самой очереди (`pgboss.job`) администратор не управляет:
pg-boss повторяет их сам по `retry_limit`, а просроченное `active` возвращает в `retry`
после `expire_seconds`.

## 12. Отзыв ссылки участника

**Не проверялось** на стенде.

- **Выпустить новую вместо старой:** `POST /api/assignments/:assignmentId/invitations`
  — прежняя ссылка и активные сессии по ней отзываются в той же транзакции.
- **Отозвать без выдачи новой:** отдельной операции нет; используется отмена
  назначения `POST /api/assignments/:assignmentId/cancel`, которая отзывает ссылки и
  сессии.
- **Отозвать доступ руководителю:** `DELETE /api/organizations/:orgId/members/:membershipId`
  — членство переводится в `revoked`, права очищаются, сессии пользователя закрываются.
- **Массовый отзыв в восстановленной копии** выполняют ограды удаления (§ 6.3).

Отсутствие операции «отозвать ссылку, не отменяя назначение» — невыполненный критерий.

## 13. Удаление данных по запросу

**Процесс не реализован (Q-01).** В базе есть таблицы `platform.privacy_requests` и
`platform.deletion_jobs`, поколение данных `core.assignments.data_generation`, признак
`processing_hold` и ограды восстановления (§ 6.3). Чего нет:

- приёма и рассмотрения запроса в продукте (API и интерфейса);
- исполнителя удаления (задания, которое действительно стирает содержание);
- журнала исполненных удалений **вне базы** — именно он нужен, чтобы после
  восстановления из копии закрыть оградой то, что было удалено после снимка
  (`RESTORE_FENCE_IDS` заполняется вручную).

Отзыв согласия участником в продукте тоже не реализован: есть только отказ от участия
(`POST /api/participant/decline`), а `core.consent_records.withdrawn_at` заполняется
не действием участника.

Пока процесса нет, удаление выполняется администратором базы вручную под ролью
владельца схемы, и каждый такой случай **обязан** попадать в журнал эксплуатации с
идентификаторами назначений: без него ограды восстановления неполны. Это
невыполненный критерий ТЗ 10.8 и блокирующая зависимость для § 6.3.

## 16. CI

`.github/workflows/ci.yml`: `npm ci` → prisma generate → format → lint → typecheck →
модульные тесты → сборка → **типы набора e2e** (`npm run typecheck:e2e`) →
`scripts/check_spec.py`; отдельный job с сервисом postgres:18 для тестов на реальной
базе (пароли runtime-ролей генерируются в job и маскируются); отдельный job собирает
образы без публикации. Кэш npm — по lockfile.

Шаг `typecheck:e2e` добавлен потому, что у `tests/e2e` отдельный `tsconfig`:
`npm run typecheck` его не покрывает, и поломка типов в e2e проходила CI незамеченной,
хотя локальный агрегат `npm run verify` этот шаг включает.

Маскируются **обе формы пароля** — исходная и percent-encoded. `::add-mask::`
действует на конкретную строку, а в `$GITHUB_ENV` уходит именно закодированная форма;
без отдельной маски пароль попал бы в журнал при любом выводе строки подключения
(упавший тест, отладочный вывод pg) в тривиально декодируемом виде.

Внешние действия закреплены по commit SHA с комментарием-версией
(`actions/checkout@fbc6f39… # v5.1.0` и т. д.): подвижный тег владелец репозитория
действия может переставить, и сборка перестала бы быть воспроизводимой — при том что
`npm ci` и версия Node закреплены строго. Обновление версии — осознанная правка SHA.

**Не проверялось:** прогон в самом GitHub Actions. Локально проверен только разбор
YAML. Шаги повторяют команды, которые проходят локально.

## 17. Известные особенности

- **Перезапуск worker после `db:reset`.** Сброс схемы пересоздаёт роли и схему
  очереди; работающий worker остаётся с недействительным подключением и паролем.
  После `npm run db:reset` и `npm run db:seed:demo` worker нужно перезапустить.
- **`NODE_ENV`.** Режим приложения задаётся `APP_ENV`. `NODE_ENV=development` в
  окружении ломает production-сборку Next.
- **Порты по умолчанию:** web 3000, api 3001, evaluator 3002, PostgreSQL разработки
  55442, тестовая база 55443. Образы публикуют 3000/3001; в `compose.app.yaml` порты
  хоста задаются `WEB_PUBLISHED_PORT` и `API_PUBLISHED_PORT`.
- **Node 24.21.0** закреплён в `.nvmrc` и `.node-version`; сборка образа отказывается
  работать на другой версии.
- **Размер образов.** Образ api ≈ 1 ГБ: `@prisma/client` тянет peer-зависимость
  `prisma` (CLI и Studio), которая в рантайме не нужна. Уменьшение — отдельная задача.
- **Компактный образ web** (`output: 'standalone'`) требует правки
  `apps/web/next.config.ts`; сейчас используется обычный `next build` + `next start`.
- **`API_HOST` принимает только IP-адрес** (`127.0.0.1`, `0.0.0.0`, IPv6). Имя хоста,
  включая `localhost`, схема конфигурации отвергает при старте с объяснением: адрес
  прослушивания не разрешается через DNS. В `.env.example` строка закомментирована.
- **read_only у web.** `next start` пишет в `.next/cache`, поэтому в
  `infra/compose.app.yaml` у сервиса web `read_only: true` дополнен tmpfs на `/tmp` и
  `/app/apps/web/.next/cache`. **Проверено 17.09.2026:** контейнер с
  `--read-only --tmpfs /tmp --tmpfs /app/apps/web/.next/cache` поднимается, `/` и
  `/login` отдают 200, ошибок записи в журнале нет.
- **Публикация портов** в `infra/compose.app.yaml` привязана к loopback хоста
  (`127.0.0.1:<порт>:<порт>`) — и для api, и для web, и для базы профиля `local-db`:
  наружу сервисы выходят через общий reverse proxy, а не напрямую.
- **Профиль `local-db`.** У сервиса `migrate` есть `depends_on: postgres` с
  `condition: service_healthy` и `required: false`: при внешней базе сервиса в запуске
  нет и это не ошибка, а при `--profile local-db` миграция ждёт готовности сервера.
  Сам профиль целиком по-прежнему **не запускался** (dev-порты и база заняты);
  проверено, что `docker compose config` валиден и с профилем, и без него.
