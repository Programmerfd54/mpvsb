## R1-01. Проверить запуск и подготовить окружение

### Где смотреть

- `README.md`, `.nvmrc`, `package.json`, `.env.example`.
- `infra/compose.yaml` — локальные базы разработки и тестов.
- `infra/compose.app.yaml`, `infra/app.env.example` — запуск приложений в контейнерах.
- `apps/api/src/modules/health/health.controller.ts` — проверки состояния API.

### Что сделать

1. Развернуть отдельную чистую копию проекта. Не использовать рабочую БД другого участника для проверки установки.
2. Установить версии Node и npm из проекта. Сейчас это Node 24.21.0 и npm 11.19.0. Не менять зависимости ради самой проверки запуска.
3. Заполнить локальное окружение по `.env.example`. Проверить, что файл с реальными значениями не отслеживается Git.
4. Поднять PostgreSQL, применить миграции, создать демоданные и запустить web, API и worker.
5. Проверить, что повторный запуск приложений не требует пересоздания БД.
6. Привязать порты локальных баз из `infra/compose.yaml` к `127.0.0.1`. Сейчас там опубликованы `55442:5432` и `55443:5432` без ограничения интерфейса. Для разработки достаточно `127.0.0.1:55442:5432` и `127.0.0.1:55443:5432`.
7. Указать в инструкции две разные базы: где живёт демонстрация и какую разрешено очищать интеграционным тестам.
8. Проверить `/health/ready`: если БД недоступна, endpoint должен возвращать HTTP 503. Сейчас он возвращает JSON со статусом `degraded`, но не меняет успешный HTTP-код. `/health/live` при работающем процессе остаётся HTTP 200.

Команды для отдельной локальной копии:

```sh
nvm use
node --version
npm --version
npm ci
npm run db:generate
cp .env.example .env
```

После заполнения `.env`:

```sh
docker compose -f infra/compose.yaml up -d
npm run db:migrate
npm run db:seed:demo
npm run dev
```

`db:seed:demo` выдаёт новые пароли. На общем стенде повторять эту команду только в согласованное время. `db:reset` в ходе проверки общего стенда не использовать.

### Как проверить

1. Открыть `http://localhost:3000/login`, войти под деморуководителем.
2. Открыть `/health/live` и `/health/ready` через тот же адрес web. В исправном состоянии оба возвращают HTTP 200.
3. Создать одно назначение и пройти демотесты. Убедиться, что появился черновик заключения: это проверяет работу worker.
4. Остановить и снова запустить приложения, не удаляя данные. Назначение и ответы должны остаться.
5. На своей тестовой установке временно остановить PostgreSQL. Проверить: `/health/live` — 200, `/health/ready` — 503. Вернуть БД и дождаться восстановления готовности.
6. Выполнить `docker compose -f infra/compose.yaml ps`. В публикации портов БД должен быть адрес `127.0.0.1`.
7. Попросить второго участника повторить запуск по обновлённой инструкции.

### Готово, когда

- [ ] Чистая установка пройдена; в передаче указаны commit и команды.
- [ ] Разработка, демостенд и тесты не используют одну очищаемую базу.
- [ ] БД локальной разработки не опубликована на всех сетевых интерфейсах.
- [ ] Проверка готовности корректно сообщает об отказе БД.
- [ ] Второй участник смог запустить проект без дополнительных неописанных действий.

## R1-02. Проверить доступы и ограничить попытки входа

### Где смотреть

- `apps/api/src/modules/auth/auth.controller.ts` и `auth.service.ts`.
- `apps/api/src/modules/participant/participant.controller.ts`.
- `apps/api/src/platform/auth`, `apps/api/src/platform/security`.
- `apps/web/next.config.ts`.
- `tests/e2e/api/tenant-isolation.spec.ts`, `participant-boundaries.spec.ts`, `csrf.spec.ts`, `data-exposure.spec.ts`.
- `packages/database/tests/rls-isolation.integration.test.ts`.

### Часть А. Проверить, кто какие данные может получить

Использовать две вымышленные организации А и Б, двух руководителей и два назначения сотрудников. Проверять прямыми HTTP-запросами, а не только скрытыми кнопками интерфейса. В существующих E2E уже есть вспомогательные функции входа, создания назначения и выдачи ссылки.

Все пути в таблице находятся под `/api/v1`.

| Проверка | Что сделать | Ожидаемый результат |
| --- | --- | --- |
| Чужая организация | Под руководителем Б запросить `/orgs/{A}/assignments/{assignmentA}` и отчёт А | HTTP 404 по текущему контракту; ни одного поля чужого назначения |
| Подмена объекта | В разрешённом запросе заменить только ID назначения/отчёта на ID из другой организации | Отказ; объект не изменён |
| Чужой тест | С сессией сотрудника А получить тест сотрудника Б и отправить ответ в него | Отказ; ответ Б не изменён |
| Смешение ролей | Cookie руководителя использовать для `/participant/attempts`; cookie сотрудника — для списка сотрудников организации | Отказ, а не автоматическая подмена роли |
| Отозванная ссылка | Выдать ссылку, отозвать её, затем обменять старый токен | Сессия не создаётся |
| Завершённый тест | После отправки попытаться изменить ответ прямым PUT-запросом | Изменение отклонено; сохранённый ответ прежний |
| Защита от чужого сайта | Повторить изменяющий запрос без нужного CSRF-токена или с чужим Origin | Отказ по текущему контракту; действие не выполнено |
| Лишние данные | Посмотреть ответ API участника | Нет ключей подсчёта, данных других сотрудников и административных полей |

CSRF здесь означает проверку, что изменяющий запрос пришёл из нашего интерфейса с нужным подтверждением, а не с постороннего сайта, использующего cookie пользователя.

Если существующая проверка проходит — записать результат. Если падает — исправить серверную проверку и добавить тест на найденный случай. Не снимать защиту, чтобы прошёл frontend.

### Часть Б. Включить ограничение попыток

Сейчас `@fastify/rate-limit` подключён с `global: false`, но не назначен маршрутам. Наличие пакета не ограничивает запросы.

1. Сначала проверить, какой IP API получает от реального браузера через Next/reverse proxy.
2. Настроить доверие только известному прокси. Внешний клиент не должен обходить лимит подменой `X-Forwarded-For`.
3. Включить ограничения для `POST /auth/login` и `POST /participant/exchange`.
4. Не использовать одну учётную запись или общий адрес прокси как единственный ключ: один клиент не должен заблокировать всем вход на демостенд.
5. Для начала использовать настраиваемые значения: 10 неудачных входов за 5 минут на пару «нормализованный email + проверенный адрес клиента»; 30 неудачных обменов ссылки за 5 минут на проверенный адрес клиента. Это стартовые настройки спринта, их нужно проверить на общем стенде.
6. Счётчики должны очищаться по истечении окна. Ответ ограничения — HTTP 429 с `Retry-After` и понятным сообщением. Не раскрывать, существует ли указанный email.
7. Лимит для обмена ссылки не распространять на сохранение ответов сотрудника.
8. Если ограничитель хранит счётчики в памяти процесса, явно записать это ограничение и запускать демостенд с одним экземпляром API. Распределённый ограничитель в этот спринт не добавлять.

### Как проверить

1. На отдельной тестовой учётной записи сделать 10 неверных входов. Следующая попытка должна получить 429. Использовать скрипт/автотест, а не нажимать кнопку вручную десятки раз.
2. Проверить срок из `Retry-After`. В автоматическом тесте использовать сокращённое окно, чтобы не ждать пять минут.
3. После истечения окна выполнить правильный вход — он должен работать.
4. Проверить вход другого клиента: его не должно блокировать поведение первого.
5. Повторить превышение лимита с разными подставленными `X-Forwarded-For`. Счётчик не должен обнуляться.
6. Повторить аналогичную проверку для неверных токенов приглашения.
7. Выполнить обычное прохождение теста с автосохранением. Запросы ответов не должны получать 429 из-за лимита обмена ссылки.
8. Просмотреть логи этих проверок: в них не должно быть паролей, токенов приглашения, cookie и содержимого ответов. Не прикладывать исходные логи с такими значениями к PR.

### Готово, когда

- [ ] Проверки прав выполнены на сервере; дефекты исправлены и покрыты тестами.
- [ ] Ограничение запросов реально срабатывает через тот же адрес, которым пользуется браузер.
- [ ] Подмена адреса в заголовке не обходит ограничение.
- [ ] Другой пользователь и сохранение ответов не блокируются ошибками входа первого клиента.
- [ ] В передаче указаны настройки, ограничения реализации и результаты проверок.

## R1-03. Исправить повтор обработки заключения

### Что сейчас не так

В `generate-report.ts` есть проверка: если запись отчёта уже существует, обработку пропустить. При ошибке генерации запись со статусом `generation_failed` тоже создаётся. Поэтому повтор может завершить задание без восстановления самого отчёта.

Отдельная проблема: `assignment.completed` и некоторые другие события не направляются в обработчик, но получают дату отправки. Экран `/admin/operations` считает их выполняющимися бесконечно.

### Где смотреть

- `apps/worker/src/jobs/generate-report.ts` — подготовка, фиксация успеха и ошибки.
- `apps/worker/src/jobs/handlers.ts`, `job-outcome.ts` — результат выполнения задания.
- `apps/worker/src/dispatcher.ts` — выдача событий обработчикам.
- `apps/api/src/modules/admin/admin-operations.service.ts` — повтор и статусы для интерфейса.
- `apps/api/tests/operations.integration.test.ts` — существующие проверки.

### Что сделать

1. Воспроизвести ошибку генерации в автоматическом тесте: тестовый провайдер первый раз возвращает ошибку, второй раз — корректный результат. Не добавлять публичную кнопку или endpoint для искусственной ошибки.
2. Разрешить восстановление отчёта со статусом `generation_failed`. Проверить обе точки, где код прекращает работу при уже существующем отчёте: до подготовки и перед записью результата.
3. Сохранить историю неудачной попытки. Успешный повтор должен создать новую корректную версию того же отчёта.
4. Сохранить защиту от дублей: повтор для уже готового отчёта не создаёт второй отчёт и не меняет опубликованный текст.
5. Проверить, что повтор не обходит отмену назначения, остановку обработки и защиту от устаревшего задания.
6. Разделить события без фоновой работы и настоящие задания. Для известных событий без работы фиксировать завершённую доставку или исключить их из списка выполняющихся задач.
7. Не помечать любое неизвестное событие успешным. Если для действия нужен обработчик, а его нет, это должно быть видно как неподдержанное/ошибочное событие. Особенно не выдавать запрос удаления данных за выполненное удаление.

### Как проверить

| Случай | Шаги | Что должно получиться |
| --- | --- | --- |
| Ошибка и повтор | Завершить назначение → получить искусственную ошибку → нажать повтор | Один отчёт, новая успешная версия, состояние ожидания проверки |
| Двойное нажатие | Повторить запрос запуска дважды | Нет двух отчётов и двух одинаковых успешных версий |
| Повтор готового | Повторить старое задание после успешной подготовки | Готовый текст и его опубликованная версия не изменились |
| Отмена | Отменить назначение и попробовать повторить старое задание | Работа не возобновилась вопреки отмене |
| Событие без работы | Завершить назначение, дождаться обработки событий | `assignment.completed` не остаётся бесконечно «выполняется» |
| Сбой остаётся | Провайдер повторно возвращает ошибку | Ошибка видна; успешное выполнение не заявлено |

Для приёмки один раз пройти восстановление через `/admin/operations`. Остальные варианты допускается проверить интеграционными тестами.

### Готово, когда

- [ ] Ошибка воспроизводилась до исправления и исправленный случай проверен тестом.
- [ ] Повтор приводит к одному доступному для проверки черновику.
- [ ] История ошибки сохранена, опубликованный результат не перезаписан.
- [ ] В списке обработки нет ложного вечного выполнения для проверенных событий.

## R1-04. Запустить CI и передать рабочую версию

CI — автоматические проверки изменений в GitHub. Файл `.github/workflows/ci.yml` уже существует; его нужно выполнить на реальном PR.

### Что сделать

1. Проверить подготовку строк подключения в CI. В `mask_encoded()` команда `::add-mask::` сейчас выводится в тот же stdout, из которого через подстановку собирается URL. Разделить вывод команды маскирования и значение пароля, чтобы в `GITHUB_ENV` попадала одна корректная строка подключения.
2. Проверить это на вымышленном пароле со знаками `+`, `/`, `=`. Реальные секреты не выводить для отладки.
3. Запустить существующие проверки типов, тестов, сборки и образов. Не объявлять CI готовым по одному успешному локальному `npm test`.
4. Интеграционные тесты запускать только на выделенной тестовой БД: они могут пересоздавать схему.
5. После объединения изменений второго участника выполнить его браузерные проверки. Если автоматическое включение браузера в CI не помещается в спринт, записать отдельный подтверждённый локальный прогон. Отсутствующий браузер или учётные данные не должны выглядеть как успешно пройденные тесты.
6. Обновить инструкцию запуска и передачу работы. Общие `docs/roadmap.json`, HANDOFF и CHANGELOG сводишь ты после получения итогов от второго участника, чтобы не править их одновременно.

Основные команды:

```sh
npm run verify
npm run build
npm run test:integration
npm run build:packages
npm run test:e2e:api
npm run docs:check
```

Для E2E сначала выполнить подготовку из `tests/e2e/README.md`. Во время приёмки установить `E2E_REQUIRE_CREDENTIALS=1`, чтобы отсутствие доступа к тестовым аккаунтам завершало прогон ошибкой, а не пропуском. Значения паролей в команду и отчёт не вставлять.

## Дополнительно, если обязательные задачи закончены

Эти пункты не входят в обещанный объём до понедельника.

1. **Полный запуск через `compose.app.yaml`.** Поднять web/API/worker и отдельную БД, проверить запуск миграций и healthcheck. Записать порядок запуска. Домен и внешний сервер для этого не обязательны.
2. **Резервная копия и восстановление.** Проверить существующие `scripts/ops/backup.sh`, `restore.sh`, `verify-restore.sh` на отдельной вымышленной базе. Не восстанавливать поверх общего демостенда.
3. **Неподдержанные сценарии.** Не разрешать публикацию нового кода сценария, который не поддерживает схема заключения. Подробность — ADR-036. Не расширять каталог и модель отчёта в этом спринте без отдельного решения.

## Что оставляем на следующие спринты

Подключение реальной AI-модели, исследования, удаление персональных данных, двухфакторный вход и подготовка к работе с реальными сотрудниками. Текущая приёмка подтверждает работу демонстрации на вымышленных данных.

## Совместная приёмка в понедельник

1. Зафиксировать один commit и подготовить отдельное демоназначение.
2. Второй участник проходит кабинет сотрудника, включая прерывание связи при сохранении.
3. Ты проверяешь появление черновика, восстановление после тестовой ошибки и отсутствие дублей.
4. Под руководителем другой организации проверить отказ в доступе к этому назначению.
5. Вместе записать принятые задачи и оставшиеся дефекты. Галочка ставится после проверки, а не после открытия PR.
