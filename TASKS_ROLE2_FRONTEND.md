# Задание разработчику: интерфейс и backend

Ты отвечаешь за весь рабочий путь: страницы, API, миграции БД, письма, серверные права и тесты. Специалист по безопасности проверит готовую реализацию и поля БД, но не проектирует за тебя основные функции. Работай в отдельной ветке и передавай изменения небольшими PR, каждый с работающим сценарием.

## Что мы строим

После развёртывания в системе уже есть компания и технический администратор. Он настраивает пространство и приглашает людей. Руководитель видит только сотрудников своих подразделений, назначает оценку и читает заключение. Сотрудник входит в свой кабинет, проходит собственные оценки и управляет профилем. Рецензент проверяет заключение до публикации, если это требуется режимом оценки.

Сейчас проект устроен иначе: администратор может создавать организации и редактировать методики, руководитель имеет настройки организации, сотрудник входит только по ссылке, подразделение хранится строкой. Это **задачи на изменение**, а не уже работающие возможности.

## 1. Технический администратор и настройка компании

Компания создаётся при развёртывании однократной bootstrap-командой. Повторный запуск не создаёт дубль и не сбрасывает пароль. В кабинете администратора **нет** кнопки создания компании. Закрой `POST /admin/organizations` для обычной сессии. Убери `/admin/methods`, `/admin/scenarios` и все действия редактирования/публикации методик и сценариев из его интерфейса; прямые API-запросы тоже должны получать отказ.

| Страница | Что на ней происходит |
| --- | --- |
| Главная `/admin` | Показывает, завершена ли настройка, проблемы с письмами, приглашения, состояние обработки и переходы к нужному разделу. Без результатов отдельных сотрудников. |
| Настройка `/admin/setup` | Пошагово: название компании → логотип → почта → шаблон письма → подразделения → руководители → проверка и завершение. Шаг можно сохранить и продолжить позже. |
| Подразделения `/admin/departments` | Создать, переименовать, назначить руководителя, посмотреть численность и архивировать. Нельзя архивировать отдел с сотрудниками, не решив их перевод. |
| Пользователи `/admin/users` | Добавить руководителя или сотрудника: ФИО, должность, email/логин, подразделение, роль. Видеть статус письма и активации. Повторить приглашение, блокировать или восстановить доступ. Физического удаления руководителя нет; история сохраняется. |
| Почта `/admin/mail` | Настроить SMTP, отправить тест, собрать письмо из логотипа, приветствия, текста, кнопки входа и подписи, посмотреть desktop/mobile предпросмотр. Пароль SMTP после сохранения не показывать. |
| Обработка и аудит `/admin/operations`, профиль `/admin/profile` | Технические ошибки и журнал действий без ответов сотрудников; собственный пароль и сессии. |

После добавления пользователя сервер создаёт одноразовую ссылку установки пароля и задание отправки. Показывай **раздельно**: «ожидает отправки», «SMTP принял», «доставлено» (только если провайдер подтвердил), «ошибка», «активирован», «срок истёк», «доступ заблокирован». Принятое SMTP письмо нельзя называть доставленным. При ошибке отправки пользователь остаётся в списке и письмо можно повторить. Технический администратор не должен случайно заблокировать последнего администратора без процедуры восстановления.

## 2. Руководитель подразделения

В меню: **Главная, Сотрудники, Оценки, Заключения, Уведомления, Профиль**. Убери настройки организации, управление доступами и списки чужих подразделений. Scope проверяется API на каждом запросе, включая прямой URL. Руководитель смотрит состав команды; создание учётных записей делает технический администратор.

**Главная.** Покажи ближайшие действия: новые/активные оценки, истекающие сроки, ожидающие заключения, новые опубликованные заключения. Каждая карточка ведёт к отфильтрованному списку. Для пустого кабинета объясни первый шаг: открыть команду или назначить оценку.

**Сотрудники.** Список и карточка показывают ФИО, должность, подразделение, текущие оценки и историю разрешённых заключений. Если руководитель отвечает за несколько отделов, есть фильтр. Не делай из результатов общий рейтинг человека.

**Перевод или повышение.** Сотрудник сохраняет свой ID. Операция содержит старый/новый отдел, новую должность при необходимости, дату и основание. Перед подтверждением покажи активные оценки и потребуй выбрать, кто продолжает работу с ними: прежний руководитель, новый или отмена с новым назначением. Прошлые оценки хранят снимок отдела и должности на момент назначения. После перевода сервер сразу меняет права доступа; открытая вкладка обновляет данные. Само право инициировать перевод выдай явно, по решению компании, а не всем руководителям автоматически.

**Создание оценки и конструктор.** Руководитель формулирует рабочий вопрос, выбирает утверждённый сценарий, видит цель и ограничения каждой методики, затем выбирает сотрудника и срок. Дай понятный предпросмотр глазами сотрудника. Конструктор позволяет сохранить локальный черновик сценария, выбрать утверждённые блоки и добавить собственные качественные вопросы. Свои вопросы помечаются как вопросы руководителя: они не получают баллов, норм и автоматического вывода. Вопросы, ключи подсчёта и интерпретацию утверждённой методики руководитель не изменяет. Версии сценария и методик фиксируются в назначении.

**Заключение.** Экран ведёт по цепочке: исходный вопрос → пройденные этапы → данные и источники → объяснение результата → ограничения → возможные следующие действия → решение руководителя. Отдели ответы сотрудника, мнение руководителя и вывод системы. Показывай отсутствие данных для непройденного этапа, не приписывай человеку диагноз, «тип личности» или вероятность увольнения. Руководитель записывает собственное решение и обоснование; система не принимает кадровое решение за него.

Владелец продукта хочет видеть, что сотрудник написал на каждом этапе. Реализуй это отдельным API и блоком в опубликованном заключении, **только** для разрешённых типов ответов, после завершения и рецензии, при заранее показанном сотруднику тексте информирования. Записывай каждый просмотр в аудит. До утверждения этого текста выдачу ответов держи выключенной; остальное заключение должно работать. Ответы другого подразделения, ключи подсчёта и черновики до публикации не выдаются.

## 3. Кабинет сотрудника

После входа у сотрудника только **Главная `/employee`**, **Оценки `/employee/assessments`**, **Настройки `/employee/settings`**. На главной новая оценка — заметная карточка «Пройдите оценку»: цель, число этапов, срок, подтверждённое время прохождения и кнопка «Начать». Если оценок нет, покажи понятное пустое состояние.

Кнопка ведёт к условиям участия, затем к этапам оценки. Используй существующий механизм сохранения ответов и прохождения `/participant/*`, связав его с учётной записью: вошедший сотрудник открывает **только свои** назначения. Ссылка из письма может открыть конкретную оценку, но не заменяет личный кабинет. Покажи прогресс, состояние сохранения, возможность паузы, возврат, проверку перед отправкой и понятное завершение.

Вопросы могут выглядеть разнообразнее: карточки выбора, шкала с подписанными полюсами, короткий текст, ранжирование, когда такой тип предусмотрен методикой. Оформление не должно менять смысл шкалы или подталкивать к «правильному» ответу. В настройках — собственные данные, подразделение, пароль, сессии и обращение по данным.

## 4. Backend и данные, которые ты реализуешь вместе с экранами

- Схема БД: подразделения с ID, привязка пользователей и руководителей, история переводов, снимок отдела/должности в назначении, состояние настройки, шаблоны писем и события доставки. Миграция старого строкового `employees.department` не должна терять сотрудников.
- API-контракты в `packages/contracts` для каждого экрана: запрос, ответ, ошибки, пагинация, версия для конфликтов, право доступа. Права не вычисляются по названию роли на клиенте.
- Серверная изоляция по организации и подразделению; отдельное право на перевод и чтение разрешённых ответов. После блокировки или перевода старые сессии/доступы пересматриваются.
- SMTP через очередь и outbox: повтор без дублей, безопасный шаблон, одноразовый токен с TTL, пароль и токен не попадают в логи и клиентский bundle.
- Сохранение ответов, подсчёт и публикация продолжают работать на зафиксированных версиях. Локальный качественный вопрос не влияет на scoring.

## Порядок работы и сдача

1. Сначала согласуй с владельцем продукта четыре правила: кто утверждает версии методик; какие ответы руководитель видит; кто видит старые заключения после перевода; кто вправе переводить сотрудника. До решения используй более узкий доступ и не включай выдачу текстов ответов.
2. Сделай роли, bootstrap, миграции и API-контракты. Затем страницы администратора, руководителя и сотрудника вертикальными срезами: экран + API + проверка доступа в одном PR.
3. Проверь четыре пути: первый запуск и приглашение; команда и перевод; назначение и прохождение; публикация заключения и фиксация решения. Используй только синтетические данные.
4. Передай КБ-специалисту PR и commit SHA, миграции, схему новых полей, матрицу прав, команды и результаты проверок, известные ограничения. Исправь его замечания до совместного созвона.

**Готово, когда** четыре пути проходят в браузере и по API; прямые обращения к чужим данным и закрытым редакторам отклоняются сервером; видны честные статусы почты; после перевода права меняются; тексты ответов выдаются только по утверждённому правилу. Проверь loading, пустое состояние, ошибку, 403, истёкшую ссылку, конфликт, успех, клавиатуру, экранный диктор, 200% zoom и телефон. Запусти `npm run typecheck`, `npm run lint`, релевантные тесты и запиши фактический результат.
